## Observed in source

### I/O and ordering

- Lines 1–52, 57–88, 106–126, 1418–1440. The comment names JC2432W328C / ESP32 Dev Module and shows the external LED data resistor and shared ground. The program is an ESP32 status display with RX-only inputs and strip output. GPIO21 is ESPSoftwareSerial RX from BLE TX at 9600, with no TX pin and non-inverted config. GPIO22 is plain INPUT for BLE STATE with 30 ms debounce. GPIO35 is HardwareSerial UART1 RX from the named MAX3232 scale output, 19200 8N1 with TX disabled. GPIO17 is a 22-pixel NeoPixel GRB/800 kHz strip, brightness 100. USB Serial is 115200. `FULL_SHOW = true`.
- Lines 1418–1440, 1493–1499. Setup begins USB Serial, waits 250 ms, initializes/clears the strip and centers the scanner, starts the sniff UARTs, configures GPIO22, and directly seeds raw, candidate and connected state from one read. Booting with GPIO22 high seeds connected without a wake edge. With no target, it goes straight to idle ember in full mode. Booting low can show startup unless target capture or a stable STATE transition cancels it first. Every loop debounces STATE first, drains BLE RX, drains scale RX, checks channel health, and then renders once. BLE target/stop changes can therefore affect scale lines queued in that loop. Serial input is processed ahead of visuals even while an animation is active.
- Lines 1289–1349, 1256–1284. Both channels retain only ASCII printable 32–126, skip CR, and flush on LF or a buffered line with strictly more than 20 ms since last byte. Each stores 159 characters plus NUL and warns if extra printable bytes were dropped. Flush still hands the truncated prefix to the parser. Byte timing and traffic-seen flags update before filtering, including for CR, LF and discarded bytes. The gap is checked after draining and timestamps are assigned when bytes are read, so an earlier wire-time gap need not split buffered bytes.
- Lines 982–999, 1153–1200, 1202–1215. BLE recognizes exact lowercase `stop`, or uppercase `T` followed immediately by a digit, plus, minus or dot. For target it calls `atof` after `T` and requires the resulting float to be >0. No end-of-number, suffix, finite, or range validation. Scale requires exact leading `ST,` or `US,` and calls `atof` on the rest. It does not validate unit, numerical conversion success, finite value or trailing text. An `ST,` frame with a nonnumeric payload can count as zero. Unrecognized prefixes are logged and skipped without breaking counters or decision windows.
- Lines 1020–1022, 1351–1368. The 1500 ms stale checks log only. BLE is disabled by default and otherwise requires connected plus prior bytes. Scale is enabled and requires prior bytes, connected, valid target, scanner/run latch, and no active decision. An incoming byte clears its reported latch, and leaving the expected-scale condition also clears that latch. The timeout does not clear a target, verdict, latch, window or partial state.

### BLE state, stop and new target

- Lines 1373–1413. Only a candidate differing from stable state for at least 30 ms calls the transition handler. Either stable edge cancels startup pending. Rising sets blue wake pending and clears disconnect pending, retaining existing target/run state. Falling clears the target and run state and clears ACK, stop, wipe and wake pending, then queues the blue disconnect. Neither edge flushes UART buffers. RX parsing itself is independent of STATE, so buffered or subsequent BLE packets can take effect after a debounced fall.
- Lines 1016–1034, 1153–1200. A duplicate requires an already valid target and float absolute difference <=0.0005 gn. It preserves all run/animation state and yields only a duplicate log. Fresh target sets the target immediately, clears the run state, clears three pending flags (below), and queues target ACK. Stop captures verdict color before clearing: green if pass, red otherwise. With a decision it uses full collapse; without a decision it uses red center pinch. It clears the target and run state, clears wake/ACK/wipe pending and queues stop. It does not clear startup or disconnect pending. Stop and fresh target handling do not check `bleConnected`. Run reset zeroes the decision window count, displayed result, removal count, last logged and animated verdict, scanner latch/counter, and resets scanner position/direction. Live reading and UART buffers are untouched.
- Lines 1006–1010, 1190–1194, 784–795, 851–920. **Fresh-target cancellation is conditional.** A fresh target clears `stopAnimPending`, `resetWipePending`, `bleDisconnectPending`, with no change to current `visualMode`. A queued, not-yet-active stop or disconnect is suppressed. An active STOP ANIM or BLE DISCONNECT keeps its own branch and timer ahead of ACK, so a new target waits for it. Example in a single BLE drain: `stop\nT71\n` from an ordinary armed/hold visual cancels the queued stop and can start ACK on the same render. If STOP ANIM was already active on entry to that loop, the ACK waits until completion. In full mode the new ACK has priority over an active RESET WIPE, overwrites `visualMode` and prevents that wipe from resuming. A higher-priority active effect may delay ACK, but takes over the prior wipe mode itself. In minimal mode ACK is suppressed and an already-rendering wipe retains priority because of its active-mode branch. A pending wipe cleared before entry is suppressed unless scale handling separately queues another. Duplicate target runs none of this cancellation logic. Similarly, a reconnect clears disconnect pending but lets a currently active blue disconnect finish ahead of the wake branch. STOP can preempt an active wake since it is above wake.
- Lines 374–382, 851–919. A new event for the same currently running stop, wake, disconnect, ACK or wipe mode does not restart that timer just by setting its pending flag. For stop, another exact stop can still update color/style because those are captured per received command. For example, two stops drained together can overwrite the first stop's result color and collapse style with the second stop's red center pinch after the first cleared the result.

### Scale decision, run and removal

- Lines 93–101, 1217–1228. When a target is valid and there is neither a settled decision nor a run latch, two consecutive parsed scale readings at **>=1.00 gn** latch the scanner. Both ST and US count. A parsed value below 1.00 resets the counter. Serial silence or an ignored raw frame does not. Once latched it stays latched through lower readings until run-state reset. A status frame can remain visibly overlaid by a higher-priority animation. The code tests weight, not weight change, cup identity or explicit throw status.
- Lines 1036–1123, 1241–1250, 384–392. A decision needs a valid target, a rolling window of four qualifying ST readings, and float max-minus-min spread <=0.04 gn. US readings wait without clearing the window. Before the first decision, an ST reading with `liveWeightGn - targetWeightGn < -0.08f` clears the window and returns. There is no upper gate and no scanner-latch prerequisite to collecting the window. A full but spread-wide window remains and rolls on the next eligible ST reading. Accepted window arithmetic mean becomes the current displayed result. Pass is float absolute displayed-mean error <=0.02 gn, fail is otherwise. After arming, the pre-arm below-target condition no longer applies. Accepted later windows can change the verdict in either direction; unstable, over-spread and removal readings preserve the previous accepted result. Samples do not expire with time. Displayed debug weights/averages use two decimal places, spreads three, target three. The comparisons use unrounded `float`.
- Lines 1125–1148, 1241–1250. Removal runs before decision updates. It is eligible only with a target and active decision. Three consecutive parsed readings **<1.00 gn** trigger, either ST or US. A reading >=1.00 resets the removal counter. The first two lows are excluded from decision updates without clearing its window. The third snapshots verdict color, resets run state while preserving the target, and sets wipe pending. While wipe remains pending, new scale lines can update the live reading and run-start counter before the function returns, but skip rolling-decision updates. If a fresh target clears wipe pending while the old wipe still renders in minimal mode, its pending-gate effect ends early.
- Lines 403–410, 1024–1033, 1094–1122. Accepted stable windows log rolling result even without a color change. Transition logging compares against the last logged verdict. Reset directly clears the stored log latch, so an OFF transition log is not assured. Since one visual update follows the whole drain, intermediate logical results logged within a burst can be superseded before rendering.

### LED state machine

- Lines 412–434, 846–976. Full mode priority is disconnect, conditional startup, stop, wake, target ACK, reset wipe, verdict transition/active verdict animation, then base. Startup requires pending + disconnected + no target. Full base is off if disconnected, ember if connected without target, verdict hold if connected with decision, otherwise heartbeat or scanner by run latch. Event overlays and verdict transition selection are independent of the disconnected base. A disconnected target frame can therefore show ACK, and an accepted disconnected decision can show one verdict entry before returning to the off base. A disconnect or stop normally clears those logical results, but line handling can reintroduce one later.
- Lines 764–844. Minimal mode suppresses startup, blue wake/disconnect, stop and ACK flags. Base is off until there is a connected, valid target with a decision. It retains green bloom and red pulse entry effects on initial or changed verdict and the cup-removal wipe. Active wipe outranks verdict effects. An active PASS/FAIL entry can complete if the result disappears without an allowed higher-priority effect, as the OFF desired state resets only `lastAnimatedVerdict` and does not change active visual mode. This can matter after stop/disconnect in minimal mode. A change from pass to fail or vice versa can replace an in-progress verdict entry.

## Revision differences from the original files

- **v1.8 baseline** already has the heartbeat-until-run latch, scanner motion, one parsed >=1.00 reading to latch using the cup threshold constant, the stop styles, and verdict entry effects in verdict-only mode. Its comments advertise THINKING, but enum/renderer/switch only exist as unreachable plumbing in the actual base path (v1.8:395–417, 665–677, 954–955). Its scale handler calls rolling decision and verdict logging before removal (v1.8:1172–1207), and it does not exclude low readings from already settled windows before removal.
- **v1.9 vs v1.8** removes dead THINKING support and the unused immediate-reset helper, names scanner start and removal as separate 1.00 constants while still latching on one eligible parsed frame, reorders removal before rolling update and excludes lows for a current result, preserves rolling average setup, cleans up verdict-transition logging, and adds per-channel overflow warnings and 1500 ms stale logging. The timeout is broad in v1.9 (prior traffic and no new byte), and truncated lines still parse.
- **v1.10 vs v1.9** adds duplicate target suppression at 0.0005 gn, raises target print precision from two to three decimals, disables BLE stale warnings by default with a connected gate if enabled, and restricts enabled scale stale warning to an unsettled active-run latch while connected and armed.
- **v1.11_BROKEN vs v1.10** adds wipe support when `FULL_SHOW=false`, but drops flag clearing when a full-show wipe completes, on stop, and on disconnect. In full mode a set wipe flag survives completion, so the next render can re-enter wipe and scale decision logic can remain blocked by the pending flag. Stop/disconnect can likewise leave an old queued wipe to follow those effects. This follows directly from the omissions, independently of the folder name.
- **v1.12 vs v1.11_BROKEN** restores the three reset flag clears. Direct v1.10-to-v1.12 diff confirms the net changes are the minimal-mode wipe support and corresponding comment. Verdict entry effects continue in minimal mode.
- **v1.13 vs v1.12** raises spread from 0.03 to 0.04 gn, adds the two-reading scanner latch and reset counter/startup print, adds fresh-target clearing of three exit flags, and replaces a redundant target-path `runVisualLatched=false` because `clearRunStateOnly` already clears it. See the cancellation distinction above.

## Derived edge cases and limits

- Float boundary example checked with IEEE-754 binary32 emulation. A range from printed 69.96 to 70.00 produces binary32 subtraction 0.040000915527, above binary32 `0.04f` (0.039999999106). The printed 0.040 spread is therefore compatible with rejection at this boundary. At 70.00 the nominal error from 69.98 is 0.019996643066 in binary32, inside `0.02f`. Source comparisons and example calculations are established. The frequency and consequences of boundary cases on the installed system are unknown.
- `updateVisuals` reads `now` before a possible `beginVisualMode` recording a second `millis()`. If those calls straddle a tick, unsigned elapsed in the new one-shot updater can wrap and meet its completion threshold immediately (e.g. lines 374–378, 778–790, 736–745). This is a source-derived execution possibility. No reproduction frequency or current symptom is established.
- Header wording describes ST windows “near target” though only the pre-arm lower bound is enforced, and describes scanner start “above” 1.00 though the code includes equality. The header describes stop as a full collapse, while the handler uses a center pinch without a result. Ordinary base is off when disconnected, but disconnected input can still queue visual overlays. Earlier summaries of verdict-only mode as solid holds only are incomplete.
- Unknown from the source audit are installed firmware and electrical wiring, measured BLE/scale traffic and frame cadence, user intent behind the revision, real LED timing, incidence of stale/overflow or parser cases, and actual runtime behavior for any example. All analysis is confined to the code and exact revision diffs.
